Tutorial: reproducible builds

A build is reproducible when the same inputs give the same bytes, so anyone can rebuild a package and check that it matches the one they were given. Rewind VM fixes every input of a build, down to its random numbers, the order its threads run in and the order its directories list in, so one build makes the same run every time. Change one of those inputs and build again: if the output changes, that input changed it, and both runs are kept to replay and compare.

The examples are tiles and plugins from examples, two small builds that each write one text file. Install Rewind as the Nix tutorial does.

Build it under eight seeds

tiles writes the pkg-config file of a small library with a Python script. The script collects the packages the library links against into a set, and Python iterates a set of strings in an order drawn from its hash seed. nixpkgs sets PYTHONHASHSEED=0 in any build that has Python as an input, so tiles unsets it, to stand for a build that runs Python some other way.

A run's seed decides every random number the build draws, Python's hash seed among them. check builds tiles under eight seeds, each with the default schedule only:

Who wrote it

rewind blame takes two runs and a file, and names the program that wrote the first byte that differs: 

$ rewind blame 8d29a01c c4bd9260 /nix/store/ihhhzc5qphjjz5vgss7swki10dwkicsb-tiles-0.2.0/lib/pkgconfig/tiles.pc
tiles.pc differs at byte 178. python3 (pid 112) wrote that byte at step 2,909 in run 8d29a01c and at step 2,909 in run c4bd9260.

22 of 227 bytes differ. The bytes from byte 178:
  8d29a01c  70 69 78 6d 61 6e 2d 31 2c 20 6c 69 62 70 6e 67  |pixman-1, libpng|
  c4bd9260  7a 6c 69 62 2c 20 70 69 78 6d 61 6e 2d 31 2c 20  |zlib, pixman-1, |

Who wrote the file in run 8d29a01c, from the last writer back:
  install (pid 122) copied it from /build/tiles/tiles.pc, starting at step 3,157. Its source already differs, so the copy did not cause the difference.
  bash (pid 112) wrote /build/tiles/tiles.pc, starting at step 2,796. It is the first writer, and the file already differs when it is done.
Run c4bd9260 made the file the same way, with the same programs.

In both runs, one write of 227 bytes, from byte 0, set byte 178.

python3 ran with the same command line in both runs, so the difference comes from something it read or from randomness.

What python3 read:
  1 file that the build made, all the same in both runs: /build/tiles/gen-pc.py.
  31 other files that the build did not make, such as programs and libraries.

Likely cause: something inside python3 (pid 112), such as randomness or the order its threads ran in. Its command line and the files the build made that it read are the same in both runs.

The first line is the answer: python3, pid 112, wrote that byte at step 2,909. The lines after it show how blame got there. install only copied a file that already differed. Before that, pid 112 opened /build/tiles/tiles.pc while it was still bash, for the > redirect, then became python3. python3 had the same command line and read the same gen-pc.py in both runs, so the cause is inside it, and the seed is the one input that changed.

Blame works from records the guest kernel keeps in every run: each write to a file, and each file a program opens. It finds the write that set the byte without replaying either run.

Fix it

Clone the repository to edit tiles:

$ git clone https://github.com/fzakaria/rewindvm
$ cd rewindvm

In examples/tiles/gen-pc.py, sort the packages before writing them:

@@ -27,5 +27,5 @@
 print("Name: tiles")
 print("Description: Tile a large image into small ones")
 print(f"Version: {VERSION}")

Directory order

plugins writes an index of the plugins it ships, in the order os.listdir returns them. Under eight seeds it reproduces: 

$ rewind check --epoch 1790985600 --seeds 8 --schedules 0 --all --no-narrow .#plugins
...
0 of 7 other runs ended differently
same result under all 8 runs

A directory lists in the order its filesystem keeps it. In the VM that order is the same in every run: /build lists its newest file first. On a real machine, ext4 lists a directory by a hash of each name, keyed by a seed chosen when the disk was formatted, so two machines can list one directory in two orders. The guest kernel does the same when its command line has rewind.dirents=N: every directory lists in an order keyed by N. Build under two keys: 

$ rewind nix --epoch 1790985600 --quiet --kernel-args rewind.dirents=1 .#plugins
rewind: run e4c221b26df20a9c exited:0 after 3885 steps, 0.097s virtual, 1.196s wall (poweroff)
/nix/store/b729hjnswi2l739nvpxzwmx4laf5ynlj-plugins-0.1.0 3d555b5412961f82  differs from your store
...

$ rewind nix --epoch 1790985600 --quiet --kernel-args rewind.dirents=2 .#plugins
rewind: run 593a9430de55e469 exited:0 after 3885 steps, 0.097s virtual, 1.160s wall (poweroff)
/nix/store/b729hjnswi2l739nvpxzwmx4laf5ynlj-plugins-0.1.0 925dde4ef23a27e2  differs from your store
...

The hash after each store path is the output's, and the two keys give two outputs. The index is the file that changed: 

$ rewind diff --file /build/plugins/plugins.txt e4c221b2 593a9430
plugins.txt differs, first at line 3.
Only in the left run: 2 lines.
Only in the right run: 2 lines.

Lines marked - are only in the left run. Lines marked + are only in the right run.
  # The plugins this package ships, one a line.
  sharpen
+ resize
  crop
- blur
  rotate
- resize
+ blur

Under each key the index names the same five plugins in another order.

The key is one of the run's inputs, so each order replays. check does not vary the key yet, and there is no --dirents option: give it with --kernel-args.

In examples/plugins/gen-index.py, sort the names:

+for name in sorted(os.listdir(directory)):
